# Architecture Decision Highlights

Короткие ответы «почему так» по решениям, которые чаще всего вызывают вопросы.
Полный реестр упрощений — [COMPROMISES.md](../COMPROMISES.md), обзор системы — [ARCHITECTURE.md](../ARCHITECTURE.md).

---

## 1. Почему circuit breaker свой, а не библиотека

**Решение:** собственная реализация (~100 строк в `services/resilience.py`), а не `purgatory`/`aiobreaker`.

- **Зависимость от одного провайдера.** У нас ровно два внешних вызова (Gemini, Grok vision API).
  Библиотечный breaker тянет конфигурацию метрик/storage, которая нужна при десятках зависимостей —
  у нас это оверхед без отдачи.
- **Интеграция с retry-queue.** Наш breaker связан с персистентной очередью повторов (Block A):
  открытый контур автоматически ставит анализ в очередь с backoff, а не просто кидает исключение.
  Стороннюю библиотеку пришлось бы обвязывать тем же кодом.
- **Тестируемость.** Собственный код покрыт детерминированными тестами переходов
  (`tests/test_resilience.py`) без симуляции времени.

**Когда пересмотреть:** если появятся >5 внешних зависимостей с разными политиками — взять
библиотеку или service mesh.

## 2. Почему нормализованный контракт вебхуков

**Решение:** все платёжные провайдеры приводятся к единой внутренней модели событий
(`routers/billing.py`), специфичные payload'ы не выходят за слой адаптера.

- **Идемпотентность в одном месте.** Каждый провайдер шлёт дубликаты и reorder-события.
  Нормализация позволяет проверять `event_id` и статус до применения бизнес-логики.
- **Замена провайдера = один адаптер.** Переход со Stripe на ЮKassa не трогает тарифы/квоты.
- **Безопасность по умолчанию.** Подпись проверяется до парсинга бизнес-данных;
  непрошедшие подпись события логируются и отбрасываются единообразно.

## 3. Почему explainable scoring (разбивка вердикта в UI)

**Решение:** UI показывает композитную разбивку — pHash similarity, ELA score,
уверенность каждого LLM при консенсусе (`frontend/src/widgets/verdict-card`).

- **Юридическая ценность.** Жалоба на маркетплейс сильнее, когда можно показать
  независимые факторы, а не «нейросеть так решила».
- **Доверие оператора.** Аналитик видит спорные случаи (LLM уверен, pHash нет) и
  осознанно направляет их в ручную проверку вместо слепого доверия.
- **Диагностика деградации.** Просадка точности конкретного фактора видна в данных
  golden set (`evals/`) раньше, чем упадут бизнес-метрики.

## 4. Почему X-API-Key, а не JWT/сессии

**Решение:** аутентификация по ключу с ролью на уровне тенанта (`services/tenancy.py`).

- **B2B-first.** Ключ нужен для partner-API в любом случае; тот же механизм обслуживает
  UI — одна модель авторизации вместо двух.
- **Нет cookie-инфраструктуры.** JWT-сессии требуют refresh-ротации, logout-листов,
  CSRF-защиты — пока нет самостоятельной регистрации пользователей, это преждевременно.
- **Фронт держит ключ в памяти** (не localStorage), CSP nginx режет инлайн-скрипты.

**Когда пересмотреть:** с появлением самостоятельной регистрации/SSO — перейти на httpOnly-cookie
сессии, оставив ключи только для machine-to-machine.

## 5. Почему фронтенд — Vite SPA на Feature-Sliced Design

**Решение:** отдельное SPA в `frontend/`, TanStack Router/Query/Table, строгие границы слоёв
(`eslint-plugin-boundaries`), старый `index.html` не тронут (мгновенный откат).

- **Внутренний дашборд, а не лендинг** — SEO не нужно; SSR/TanStack Start избыточны.
- **Server-state ≠ client-state**: ответы API живут только в TanStack Query (кэш, ретраи,
  поллинг), Zustand — лишь UI-предпочтения.
- **Контракт статусов батча зафиксирован тестами**: MSW-тест падает при любом дрейфе
  (`completed|error` vs легаси `done`) — именно этот класс бага ломал первую версию.
- **Границы FSD проверяет линтер**, а не дисциплина разработчиков.

## 6. Почему nginx раздаёт фронт и проксирует /api

**Решение:** multi-stage Dockerfile → nginx; `/api/*` проксируется на FastAPI.

- **Same-origin = ноль CORS** ни в проде, ни в CI.
- **CSP без `unsafe-inline`** для скриптов (Vite хэширует бандл), immutable-кэш ассетов,
  no-cache для `index.html`.
- **`VITE_API_URL=/api/v1` относительный** — сборка не зависит от окружения.

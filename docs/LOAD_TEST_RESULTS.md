# Результаты нагрузочного тестирования (A-C4)

**Важно: это цифры с локальной dev-машины, НЕ с production-железа.** Целевого
прод-окружения для прогона в этом репозитории нет. Числа ниже показывают
относительный порядок величины и подтверждают, что деградация (circuit breaker
+ retry-queue) действительно работает под нагрузкой — не воспринимайте их как
прод-SLO без повторного прогона на реальном железе перед публичным запуском.

## Окружение прогона

| | |
|---|---|
| Дата | 2026-08-29 |
| Коммит | `3f0e2a7` |
| Машина | Apple M2, 8 vCPU, 16 GB RAM (локальный dev-ноутбук, НЕ прод) |
| Python | 3.11.15 |
| Сервер | `uvicorn app.main:app --workers 1` (однопроцессный — как в текущем `docker-compose.yml`) |
| LLM-провайдер | `PROVIDER=mock` (`app.llm_provider.MockProvider`, A-C4) — без сети, без реальных
  вызовов Gemini/Grok (платные внешние API в этом прогоне не использовались) |
| БД | Отдельный чистый SQLite per-run |
| Locust | 2.46.4, `loadtests/locustfile.py` (без изменений сценария) |

Прогон через `MockProvider` намеренно не включает latency реального
LLM-провайдера (Gemini/Grok) — она добавляется отдельно и варьируется по
сети/квоте, а замерять её живыми платными вызовами без явного разрешения
пользователя на платные внешние API-запросы в рамках этой задачи не
разрешено (см. правила проекта). Цифры ниже отражают **накладные расходы
самого приложения** (роутинг, БД, идемпотентность, форензика, circuit
breaker) — то, что действительно можно оптимизировать в коде FakeDetect.

## Сценарий 1 — baseline (happy path)

`locust -f loadtests/locustfile.py --host http://127.0.0.1:8010 --headless -u 20 -r 5 --run-time 45s`

20 пользователей, `MockProvider` без искусственной задержки/сбоев.

| Эндпоинт | Запросов | Ошибок | p50 | p95 | p99 | Max |
|---|--:|--:|--:|--:|--:|--:|
| `POST /api/v1/analyze` | 348 | 0 | 32 ms | 250 ms | 650 ms | 687 ms |
| `GET /api/v1/history` | 126 | 0 | 6 ms | 45 ms | 110 ms | 130 ms |
| `GET /health` | 198 | 0 | 6 ms | 65 ms | 140 ms | 346 ms |
| **Всего** | 672 | 0 (0%) | 21 ms | 160 ms | 370 ms | 690 ms |

Устойчивый RPS в этом окне: **~15 req/s** суммарно (~7.8 req/s на `/analyze`)
при 20 одновременных пользователях, 0% ошибок.

## Сценарий 2 — деградированный провайдер (circuit breaker / retry-queue)

`locust -f loadtests/locustfile.py --host http://127.0.0.1:8011 --headless -u 10 -r 5 --run-time 30s`,
сервер поднят с `MOCK_PROVIDER_DELAY_SECONDS=1.5 MOCK_PROVIDER_FAILURE_RATE=1.0`
(каждый вызов провайдера — гарантированный сбой после задержки).

| Эндпоинт | Запросов | Ошибок (HTTP) | p50 | p95 | p99 | Max |
|---|--:|--:|--:|--:|--:|--:|
| `POST /api/v1/analyze` | 54 | 0 | 1800 ms | 4900 ms | 5000 ms | 5043 ms |
| **Всего** | 128 | 0 (0%) | 8 ms | 4900 ms | 5000 ms | 5043 ms |

Проверка `GET /health` сразу после прогона:

```json
{"llm_providers": {"mock": {"configured": true, "circuit_state": "open"}},
 "retry_queue_pending": 53}
```

**Вывод**: под гарантированно падающим провайдером circuit breaker открылся
(`circuit_state: "open"`), и приложение НЕ отдавало 500 клиентам — запросы
уходят в retry-queue (Block A.6, `retry_queue_pending: 53`) вместо ошибки.
Это подтверждает заявленное поведение "202 + опрос вместо мгновенного 500"
под нагрузкой, а не только в юнит-тестах.

## Что дальше

- Повторить оба сценария на реальном prod-железе (или максимально близком
  staging) перед тем, как заявлять эти цифры клиентам как SLO.
- Отдельно замерить latency реального LLM-провайдера (Gemini/Grok) —
  требует явного разрешения на платные вызовы, не запрошено/не выполнено в
  рамках этой задачи.
- CI: `nightly-loadtest.yml` (см. `.github/workflows/`) прогоняет
  Сценарий 1 на каждый релизный тег — деградация видна автоматически, не
  постфактум на проде.
